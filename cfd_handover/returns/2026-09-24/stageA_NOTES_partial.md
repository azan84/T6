# stageA_NOTES_partial.md (2026-09-24) - caveats for stageA_summary / stageA_A2_sweep / stageA_A5_ladders / item1_tree / item5_rcr / item6_cost

Numbers come from the retained raw monitors (`postProcessing/*/surfaceFieldValue*.dat`), the case files (`0/p`, `system/*`, `meshDict`), the retained solver logs where they exist, and (for the throat resolution) the retained meshes.
Pressures in the monitors are kinematic (m2/s2); FFR = p_measurement * 1060 / 11998.98 at x = 56.5 mm; throat Re = 4 rho Q / (pi mu D_throat). "Report" = STAGE-A-VALIDATION.pdf as of 2026-09-24.

## What exists and what does not
- Retained solver logs: Item 1 (4 cases), Item 2 sten60/sten65/level4, Item 5, Item 6 (smoke test + the two stopped runs). NOT retained: any log for A1, A2/A3, A4, A5 (Stage A). So for Stage A the residual columns are the report's text (marked as such), checkMesh statistics exist only for A1 and sten00 (from the report) and the numeric statistics are blank for the other Stage A cases, and wall-clock is derived from file timestamps (monitor file birth -> last write), not from a log.
- Cores for the Stage A runs come from `system/decomposeParDict` (8). Cases with no decomposeParDict and no processor directories are listed as "1 (inferred)". Peak RAM was never recorded for any of these runs.
- Every wall-clock in these files is contended: several Stage A solves ran at the same time (column `stageA_ranks_running_concurrently_at_some_point`), and Items 1/2/5/6 ran together on 2026-09-19 with load average up to 78. Do not use them as cost figures.

## Places where the monitors differ from what the report says (all pass/fail verdicts unchanged unless stated)
1. **A4 step 2 (round trip).** Report: Q = 1.130642e-6, error -0.0120 %, "stopped once confirmed stable". Monitor: that value is what the flux showed at iterations ~377-435; the run was not stopped, it continued to 2000 and the flat final value is 1.13078875e-6 (+0.00098 % against the step-1 target 1.130777639e-6). Both are far inside the 0.5 % tolerance.
2. **A2 sten50.** Report: "stopped early ... well before the 2000-iteration budget". The retained monitor has 2000 rows (flat from about iteration 800), i.e. the run reached its full budget.
3. **A5 sten70 fine.** Monitor FFR 0.787905; the report's 0.787932 comes from the independent field extraction after the log incident (difference 2.7e-5). Two monitor files exist (original run and the accidental t = 0 restart), 3000 rows each; they agree over the last 500 iterations to 4.5e-9 (relative difference of the means) but are NOT identical over the run (the two pressure histories differ by up to 3.3e-2 relative at iteration 4, in the start-up transient; corrected 2026-09-26 after the Astra audit). Finest-pair difference: 0.004705 (monitor) vs 0.004732 (report); both under 0.005.
4. **Item 2 level 4 (the 1.89 M-cell sten70 mesh) - this one matters.** The report's FFR 0.792712 is the last-100-row mean ending at iteration 594. The run continued to iteration 896, where the last-100 mean is **0.792342** (band 0.000027) and still drifting at -6.5e-5 per 100 iterations. The final-iteration initial residuals are Ux 2.0e-4, Uy 1.5e-2, Uz 1.0e-2, p 6.9e-4 (solve.log): NOT converged to 1e-5 and not "genuinely converged" by the report's own residual standard; the report's statement rests on the monitors alone. Differences with the monitor value: medium->fine +0.004705, fine->level4 +0.004437 (report: +0.004780) - still not shrinking (ratio 0.94). Celik GCI recomputed by me for reference only, with level4 = 0.792342 and fine = 0.787905 (r21 = 1.354, r32 = 1.261): apparent order p = 1.23, GCI_fine = 1.55 %, U_FFR = 0.0123 (report: p = 0.97, 2.21 %, 0.0175). U_FFR is still 2.5x the 0.005 tolerance, so "GCI not trustworthy / A5 pass not established" stands, but the quoted GCI numbers change and the level-4 point itself is not a converged value.
5. **Item 1 BC error.** Report table: -0.0003 %, -0.0003 %, -0.0002 % (ds 0 %), +0.00003 % ... (ds 60 %). From the last monitor row: +0.00016 / +0.00009 / +0.00007 % (ds 0 %, hand variant), +0.00018 / +0.00011 / +0.00009 % (ds 0 %, auto), |error| <= 2e-5 % at ds 60 %. The two ds 0 % cases were stopped by hand at ~1200 iterations with the flux still drifting ~0.002 % over the last 200 iterations (no residualControl by design), so their fourth decimal depends on the row read. Flow-split gaps recomputed today from the same `build_0d.py`: ds 0 % B1/B2 -1.02 / -1.03 % (report -1.03 / -1.05), ds 60 % B1/B2 -1.01 / -1.02 % (report -1.01 / -1.03); differences <= 0.02 percentage points, cause not investigated. The mesh check was run once per severity on the hand-variant mesh.
6. **Item 5.** Report: 17,316 timesteps, max Courant 0.52, mean 0.044. Log: 17,311 timesteps; max Courant 0.62 over the whole run (0.52 over the last 100 steps); mean of the step means 0.0405 (0.0422 over the last 100). Error metrics reproduce exactly (max 0.2827 %, mean 0.0424 %, 8656 cycle-2 samples, 1195 backflow samples). Error is normalised by max |p_ref| over cycle 2, not point-wise.
7. **Item 6 "isolated pre-contention" timing was not isolated.** The smoke test ran 12:54:11-12:56:35 on 2026-09-19; the solve.log start times show Item 2's sten60/sten65/level4 (4+4+8 ranks, since 12:47:44) and Item 5 (4 ranks, since 12:44:47) running at the same time, i.e. at least 20 other MPI ranks on 16 physical cores. The 7.37 s/step (ExecutionTime) / 8.6 s/step (ClockTime) at 8 ranks and the 28-33 h projection are therefore not clean; the report's "~7.15 s" is not reproduced exactly (steps 2-17 give 7.37). The work order's Task 4 (isolated 200-step timing) is still the way to get a real number.

## Measured cells across the throat (work-order requirement)
Method: exact run-length of the containing cell along the throat diameter at x = 31.5 mm (+7 um in x, offset 5 um across, 6000 samples) on each retained mesh, both transverse directions (they agree to 0-1 cell). `cells_across_throat_diameter_y` = all cells including the boundary layer; `cells_across_throat_outside_BL` = that minus the 8 boundary-layer cells (4 layers per side, thickness ratio 1.2 confirmed in the measured stacks).
- sten70 (D = 0.891 mm): coarse / medium / fine / level4 = 12 / 12 / 14 / 18 total; 4 / 4 / 6 / 10 outside the BL; core cell 164.6 / 142.9 / 113.8 / 82.1 um (D/core 5.4 / 6.2 / 7.8 / 10.9). Refinement ratios of the core cell size: 1.15, 1.26, 1.39 (not 2).
- sten80 (D = 0.594 mm): coarse / medium / fine = 10 / 12 / 12 total; 2 / 4 / 4 outside the BL; core cell 126.9 / 109.7 / 95.0 um (D/core 4.7 / 5.4 / 6.25). Core ratios 1.16, 1.15. The spec's ">= 12 cells across the throat" is met only if the 8 BL cells are counted; the sten80 medium and fine levels are the same number of cells across the throat.
- Boundary-layer stack: nLayers 4 and thicknessRatio 1.2 are identical in every meshDict, but the realised first-layer / stack thickness is not monotone in refinement. sten70 BL stack per side (4 layers): 138 / 159 / 111 / 63 um (coarse..level4); sten80: 167 / 93 / 106 um (coarse, medium, fine). The medium sten70 and the fine sten80 have thicker stacks than the next-coarser level. This is consistent with, and a candidate contributor to, the non-monotone ladders; it is not shown to be the cause. Any new ladder should record the realised BL thickness per level.
- Report statements about the resolution ("~3.5 cells across the throat" for sten80 coarse, "~6" for fine) are close to the D/core numbers here (4.7 and 6.25) but not to the total counts.
